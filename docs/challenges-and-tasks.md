# Challenges and Tasks

## Overview

**Challenges** are time-bounded sprints attached to a project. They define the scope, reward pool (CP), and — optionally — a timeline for a period of work. Dates are optional: a challenge can be created with no `start_date`/`end_date` at all.

**Tasks** are a personal organizational tool inside a `type: 'code'` challenge. Each contributor who joins the challenge gets their own board (todo → in progress → done); tasks are **purely organizational** and never influence the score. The actual evaluation is triggered by the contributor once their board is done, and scores the whole project — see [Evaluating the project](#evaluating-the-project) below.

For the full rationale and design history, see the spec:
[`docs/superpowers/specs/2026-08-28-code-challenge-personal-boards-design.md`](./superpowers/specs/2026-08-28-code-challenge-personal-boards-design.md).

### Challenge types

A challenge has a `type`: `code` (the default), `ml`, or `validation`.

- **`code`** challenges work as described in this document — personal task boards, a per-contributor workspace, and a project-wide evaluation triggered by the contributor.
- **`ml`** challenges are for dataset/model/packaging work. They have **no tasks at all** — contributors submit directly through a dedicated ML workspace flow, scored and rewarded live. See [`ml-rewards.md`](./ml-rewards.md) for that entire flow. Code challenges now follow the same live-reward philosophy (see below), just with a different workspace and evaluation shape.
- **`validation`** challenges have no tasks and no repos of their own — they link 1:1 to an existing `ml` challenge (`source_challenge_id`) and let contributors manually test its submitted API packagings by dropping a file and seeing the live output. See [`validation-challenges.md`](./validation-challenges.md).

## Challenge lifecycle

```
draft → active → closed
```

| Status | Description |
|--------|-------------|
| `draft` | Challenge created but not yet started. Team can be set up, repos linked. |
| `active` | Work is happening. Contributors can join, work their board, and trigger evaluation. |
| `closed` | Challenge is over. For code (like ML), closing just flips the status — rewards are already paid out live, per evaluation run, while the challenge was active. |

A challenge is closed via `POST /api/challenges/:id/close`. Unlike the old model, this route no longer computes or distributes anything for code challenges; it exists purely to stop new joins/evaluations.

## What a challenge contains

- **Team** — contributors assigned to the challenge (`challenge_teams` table). For code challenges, this row also carries each contributor's personal **workspace** (see below) — it's their participation record, not just membership.
- **Repos** — repositories linked to the challenge (`challenge_repos` table): GitHub for code challenges in `provided_repo` mode, GitHub and/or Kaggle for ML challenges — each with an optional workspace (e.g. a branch)
- **Tasks** — personal board items, code challenges only (see below)
- **Contributions** — recorded units of output, generated by the evaluation pipeline or added manually
- **Documents** — small markdown notes attached to the challenge (`challenge_documents` table) — write-ups, decisions, links, not a general file-upload system
- **Sync Meetings** — team meetings created from the app for this challenge
- **Repo activity** — a live, on-demand view of each linked repo's recent activity (GitHub commits/PRs/reviews, or Kaggle dataset/model info), fetched from the external API rather than stored
- **Discussion signals** — an optional Slack channel plus a set of AI-detected contribution signals with fixed CP rewards, configured from the edit drawer (both `code` and `ml` challenges) — see [`slack-signals.md`](./slack-signals.md)

## Workspace modes (code challenges)

Chosen once, at challenge creation (`challenges.workspace_mode`):

- **`provided_repo`** — the challenge owns a GitHub repo (`challenge_repos`). When a contributor joins, the provisioner creates a personal branch for them, named `contrib/<challenge-index>-<username>` (protected so only that contributor can push to it).
- **`own_repo`** — no repo is created for the challenge. Each contributor declares the URL of their own **public** GitHub repository from their board, via `PATCH /api/challenges/[id]/workspace`. Private repos are out of scope for v1.

Either way, the workspace lives on the contributor's `challenge_teams` row (`workspace_provider`, `workspace_ref`, `workspace_url`, `workspace_status: pending | ready | failed`), not on a task.

## Tasks

A task is an item on a contributor's personal kanban board.

### Task fields

| Field | Description |
|-------|-------------|
| `title` | Short description of what needs to be done |
| `description` | Detailed instructions |
| `status` | Stored as `todo` / `in_progress` / `done`. Dragging the card on the board just does a `PATCH /api/tasks/[id]` of the status — no assignment, no provisioning happens on drag. |
| `challenge_id` | The parent challenge |
| `user_id` | `NULL` for a **template** task (defined by the admin/manager); a user's uuid for a task on that user's personal board |
| `parent_task_id` | Optional parent, for sub-tasks |

There is no more `type` (`solo`/`concurrent`) or `repo_id` on a task — tasks don't carry a workspace or a lock anymore.

### Template vs. personal tasks

An admin or project manager can optionally define **template** tasks (`user_id NULL`) on the challenge. When a contributor joins, every template task is copied into their own board (`user_id = them`, `status: 'todo'`); sub-tasks are copied too, remapped to the new parent. A challenge with no template just gives new joiners an empty board.

From then on, each contributor's board is entirely their own: they can create, edit, and delete their own tasks and sub-tasks freely, but cannot touch another contributor's tasks or the template (only the manager/admin can edit the template).

Fetch scope: `GET /api/tasks?challenge_id=…&scope=mine|template|all`.

## Evaluating the project

There is no more per-task evaluation. Once a contributor has **at least one task and all of their personal tasks are `done`**, and their workspace is ready (branch `ready`, or repo URL filled in for `own_repo`), they can trigger a project-wide evaluation from their board:

`POST /api/challenges/[id]/project-evaluation`

1. Checks the preconditions above and rejects if an evaluation is already `running` for that contributor.
2. Upserts a `contributions` row of `type: 'project'` for `(challenge, contributor)` — the code equivalent of the ML `dataset`/`model`/`api_packaging` contribution types.
3. Fire-and-forget (same pattern as the ML flow): snapshots the branch (`provided_repo`) or the public repo (`own_repo`) via the reused evaluation pipeline (≤ 100 commits, aggregated snapshot), scores it against the `code` evaluation grid, and normalizes the result to a **score out of 10**.
4. Writes reward ledger rows and flips `evaluation_status` to `done` (or `failed`).

The UI polls `evaluation_status` (`pending | running | done | failed`) the same way the ML flow does.

A contributor can iterate: add more tasks (this reopens the board as "incomplete" and disables the button), improve the code, put everything back to `done`, and relaunch. Only one `running` evaluation per contributor at a time.

### Rewards

Each challenge carries `reward_rules` (JSON, versioned, code-specific schema — `{ version: 1, delivery: { fixed, cap } }`). A successful run can write up to two `reward_entries` rows:

| `rule_key` | Raw points | When |
|---|---|---|
| `code_fixed` | `rules.delivery.fixed` | the evaluation completes at all (deliverable accepted) |
| `code_quality` | `rules.delivery.cap × score / 10` | every run, scaled by the agent score |

Points are paid as the **positive delta** against what was already paid for that `rule_key` on that challenge/user — a run that scores lower than a previous one pays 0 and never claws anything back; the fixed part is effectively paid once, on the first successful run. Amounts are clamped to whatever remains in the challenge's pool, exactly like the ML ledger (`RewardEntryRepository.createManyAndSyncRewards` — the same trigger that keeps `contributions.reward` in sync for ML also handles code).

`challenges.completion` for a code challenge is the fraction of the pool paid out so far (same definition as ML), not a ratio of done tasks.

## Admin workflow (typical)

1. **Create a challenge** in the admin panel — set title, description, project, type (`code` or `ml`), reward pool, reward rules, and optionally dates. For `code`, also choose the workspace mode (`provided_repo` requires linking a GitHub repo; `own_repo` doesn't).
2. **Link repos** — attach the relevant GitHub repositories (or Kaggle dataset/model repos for an `ml` challenge). Not needed for `own_repo` code challenges.
3. **Optionally define a template** — a handful of tasks (`user_id NULL`) that every new joiner's board starts from.
4. **Add team members**, or let contributors self-serve via `POST /api/challenges/:id/join`.
5. **Monitor progress** — the manage view shows each participant's board progress (x/y done), workspace status, last score, and points paid — not the detailed board itself (v1 doesn't expose other contributors' boards).
6. **Close the challenge** once done — `POST /api/challenges/:id/close` just flips the status; nothing is computed at close time for code challenges.

### Project managers

An admin can designate a contributor as the **manager** of a project (`/admin/projects`). That contributor then gets a management view for all of that project's challenges — edit details/status, create meetings, manage documents and repos, edit the task template — without needing the admin role or access to `/admin/**`. See [`auth.md`](./auth.md#project-managers-not-a-role) for exactly what a manager can and cannot do.

## Contributor workflow

1. **Join a challenge** via `POST /api/challenges/:id/join`. This creates your `challenge_teams` participation, copies the template into your own board, and (in `provided_repo` mode) provisions your personal branch.
2. **Work your board** — create/edit/reorder your own tasks, drag them through `todo → in_progress → done` (`PATCH /api/tasks/[id]`).
3. **Set your workspace** — in `own_repo` mode, declare your public GitHub repo URL via `PATCH /api/challenges/[id]/workspace`; in `provided_repo` mode, your branch is already provisioned for you.
4. **Trigger evaluation** once your board is fully `done` and your workspace is ready: `POST /api/challenges/[id]/project-evaluation`.
5. **Earn CP immediately** — points from a successful run land on your ledger as soon as the run completes, no need to wait for the challenge to close. You can iterate and relaunch for more.

---

## Linking tasks to contributions

Tasks are purely organizational and never become a contribution directly. For a code challenge, `POST /api/challenges/[id]/project-evaluation` creates/updates a single `contributions` row of `type: 'project'` per contributor, scoring their whole delivery — see the spec for the full pipeline. For an ML challenge, a contribution is created directly from the ML workspace submission flow instead (no task involved) — see [`ml-rewards.md`](./ml-rewards.md).

## Data model

```
projects (manager_id → users, optional)
  └── challenges (type: code | ml, workspace_mode for code)
        ├── challenge_teams  → users (+ workspace_provider/ref/url/status for code)
        ├── challenge_repos  → repos
        ├── challenge_documents
        ├── tasks (code challenges only; user_id NULL = template, else personal board)
        ├── contributions    → users (type 'project' for code)
        ├── reward_entries   → users (rule_key: code_fixed | code_quality)
        └── sync_meetings
```

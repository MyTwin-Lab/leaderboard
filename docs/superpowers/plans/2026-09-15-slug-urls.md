# Plan — URLs à slug pour les challenges et les sandboxes

**Date :** 2026-09-15
**Branche :** `main` (commits scopés, poussés après validation locale)
**Objectif :** `/challenges/<uuid>` → `/challenges/<slug>`, `/sandbox/<uuid>` → `/sandbox/<slug>`, sans casser un seul lien existant (liens partagés, invitations de groupe, notifications), avant que Google n'indexe les pages de détail.

---

## 0. Décisions

| # | Décision | Pourquoi |
|---|---|---|
| D1 | **Les API restent sur l'UUID.** Seules les *pages* passent au slug. La page serveur traduit le slug en UUID et le passe au composant client. | ~45 routes `/api/challenges/[id]/*` font `findById(id)` et des jointures sur `challenge_id`. Les faire accepter un slug est un chantier sans bénéfice : les URLs d'API ne sont ni partagées ni indexées. |
| D2 | **Toute ancienne URL redirige en 308** vers l'URL canonique, query string conservée : `/challenges/<uuid>`, `/challenges/<uuid>/manage`, `/sandbox/<uuid>`, et un ancien slug (voir D3). | Liens déjà partagés (invitations `?group=` collées dans Slack), notifications en base, liens tapés à la main dans les briefs markdown. |
| D3 | **Le slug est modifiable après création, et l'ancien reste une redirection** (tables `challenge_slug_redirects` / `sandbox_slug_redirects`). *Validé le 2026-09-15.* | Corriger une faute ou raccourcir un slug (ex. `mykine`) sans casser les liens ni perdre le référencement acquis. |
| D4 | **Namespaces séparés** : un challenge et un sandbox peuvent avoir le même slug. | Chemins différents (`/challenges/…`, `/sandbox/…`). Une promotion peut ainsi garder le slug du sandbox. |
| D5 | **Unicité portée par la base** (index unique) **et vérifiée en direct** dans les formulaires (endpoint de disponibilité). | L'index est la seule garantie sous concurrence ; la vérif live est l'UX. |
| D6 | **Le titre ne pilote le slug qu'à la création**, tant que l'utilisateur n'a pas touché au champ. Modifier le titre d'un challenge existant ne change jamais son slug. | Une URL ne doit pas bouger en silence. |
| D7 | **Les URLs admin restent sur l'UUID** (`/admin/challenges/<uuid>`). | Privées, jamais indexées. Hors périmètre. |
| D8 | **Un slug inconnu renvoie un vrai 404** (`notFound()`), plus un 200 + `noindex`. | Soft-404 relevé dans l'audit SEO. |
| D9 | Le segment de route `[id]` est renommé `[slug]` pour `app/challenges` et `app/sandbox`. | Le nom dit ce que le segment contient désormais. |

Arbitrages du 2026-09-15 : **D3 validée** (slug modifiable, anciens slugs redirigés) ; **§8.4 validé** (correctif du jeton d'invitation perdu à la connexion, en commit séparé).

## 1. Règles du slug — `packages/database-service/domain/slug.ts` (pur)

Un seul module, importé par les repositories, le script de migration, les schémas Zod et les formulaires client.

- Format : `^[a-z0-9]+(?:-[a-z0-9]+)*$`, **3 à 80 caractères**.
- Refusés : une forme d'UUID (sinon ambiguïté avec la redirection D2), une petite liste réservée (`new`, `edit`) pour garder de la place à de futures routes statiques.
- `slugify(title)` : NFKD, suppression des diacritiques, `&` → `and`, apostrophes supprimées (`patient's` → `patients`), tout le reste → `-`, tirets fusionnés et rognés, coupe à 80 sur une frontière de mot. Vide (titre en emoji…) → repli `challenge` / `sandbox`.
- `slugCandidates(base)` : `base`, `base-2`, `base-3`… (base raccourcie si le suffixe dépasse 80).
- `slugProblem(value)` : message lisible (`too short`, `looks like an id`, …) partagé API/formulaires.
- **Ne pas fusionner avec `packages/provisioner/src/utils.ts#slugify`** : il nomme les branches Git des challenges (garde `_`), le changer renommerait le schéma des futures branches.

Tests : accents (`Détection de lésion ligamentaire du genou (IRM)` → `detection-de-lesion-ligamentaire-du-genou-irm`), tiret long (`Validation clinique qualifiée — API…`), titre trop long, titre vide, forme UUID, suffixes.

## 2. Base de données et migration

### 2.1 Schéma

- `challenges.slug varchar(80) NOT NULL` + `idx_challenges_slug` unique.
- `sandboxes.slug varchar(80) NOT NULL` + `idx_sandboxes_slug` unique.
- `challenge_slug_redirects (slug varchar(80) PK, challenge_id uuid NOT NULL REFERENCES challenges(uuid) ON DELETE CASCADE, created_at timestamp NOT NULL DEFAULT now())` + index sur `challenge_id`. Idem `sandbox_slug_redirects`.

Miroirs : `packages/database-service/db/drizzle.ts` et `drizzle/0022_slugs.sql` (écrit à la main, comme `0021_notifications.sql`).

### 2.2 `scripts/db-apply-schema.ts` — même chemin en local et en prod

Ajouté **en fin de tableau**, dans cet ordre :

1. `ALTER TABLE challenges ADD COLUMN IF NOT EXISTS slug varchar(80)` (nullable), idem `sandboxes`.
2. **Backfill en TypeScript** (le type d'entrée du tableau passe à `{ label, sql } | { label, run }`) : dans une transaction par table, lit toutes les lignes `ORDER BY created_at, uuid`, calcule les slugs manquants avec `planSlugBackfill()` (pur, testé) et les écrit. Chaque attribution est loguée (`uuid → slug`) : le log de déploiement Scalingo garde la trace exacte.
   - Déterministe (ordre stable) et **idempotent** : sans ligne `slug IS NULL`, rien n'est écrit.
   - Dédoublonne contre les slugs déjà posés : un challenge créé entre deux déploiements garde le sien.
   - Aucune dépendance à une extension Postgres (`unaccent`) : c'est le `slugify` de l'app qui calcule, donc la prod reçoit exactement ce que l'UI aurait proposé.
3. `ALTER COLUMN slug SET NOT NULL` (rejouable sans effet).
4. `CREATE UNIQUE INDEX IF NOT EXISTS idx_challenges_slug …`, idem `sandboxes`.
5. `CREATE TABLE IF NOT EXISTS challenge_slug_redirects …`, idem `sandbox_slug_redirects`.

### 2.3 Fenêtre de déploiement (vérifié dans la doc Scalingo)

Le `postdeploy` tourne pendant que **l'ancienne version sert encore le trafic** ; la nouvelle ne le reçoit qu'après succès. Conséquences :

- Pendant l'ajout de la colonne et le backfill, l'ancien code lit sans problème.
- Entre le `SET NOT NULL` et la bascule du routage (quelques secondes), une création de challenge ou de sandbox par l'ancien code échouerait. Risque accepté (action rare) : déployer à un moment calme.
- Si le postdeploy échoue **après** le `SET NOT NULL`, l'ancien code reste en ligne et ne peut plus créer de sandbox. D'où les étapes slug **en toute fin** du script : il ne reste derrière que `db:resync-rewards`. En cas d'échec : `ALTER TABLE … ALTER COLUMN slug DROP NOT NULL` sur les deux tables rétablit l'ancien code immédiatement.

### 2.4 Données locales ≠ prod

Le backfill ne dépend d'aucune donnée précise : il marche sur n'importe quel contenu. On le vérifie sur trois bases (§13) : une copie de la base locale actuelle, une base neuve seedée, puis la base locale réelle. En prod : sauvegarde manuelle Scalingo avant le push, et en option un aperçu en lecture seule (`scripts/db-preview-slugs.ts`, via `scalingo db-tunnel`) qui affiche les slugs que le backfill attribuerait, sans rien écrire.

## 5. Pages et redirections

### 5.1 Résolution — `lib/server/pageRefs.ts` (server-only, `cache()` par requête)

`resolveChallengeRef(param)` / `resolveSandboxRef(param)` :

1. slug courant trouvé → `{ kind: 'found', entity }`
2. forme d'UUID et ligne trouvée → `{ kind: 'moved', slug }`
3. ancien slug présent dans l'historique → `{ kind: 'moved', slug }`
4. sinon → `{ kind: 'missing' }`

La résolution ignore la visibilité : un brouillon s'ouvre par son slug pour son manager, exactement comme par son UUID aujourd'hui. La visibilité reste décidée par l'API et par `lib/server/seo.ts`.

### 5.2 Routes (`[id]` → `[slug]`)

- `app/challenges/[slug]/page.tsx` : résout → `moved` : `permanentRedirect('/challenges/<slug>' + query)` ; `missing` : `notFound()` ; `found` : pré-remplissage SSR sous les clés **UUID** et `<ChallengeDetailClient challengeId challengeSlug knownAnonymous? />`.
- `app/challenges/[slug]/manage/page.tsx` : devient un composant serveur, même résolution, redirection vers `/challenges/<slug>/manage`, rend `<ChallengeManageView challengeId />`.
- `app/challenges/[slug]/layout.tsx` : `generateMetadata` et JSON-LD depuis l'entité résolue ; `moved` / `missing` → `unindexedMetadata`. La redirection est faite dans chaque page, pas dans le layout, qui ne connaît pas le sous-chemin (`/manage`).
- `app/sandbox/[slug]/page.tsx` et `layout.tsx` : idem, `<SandboxDetailClient sandboxId knownAnonymous? />`.
- `app/admin/challenges/[id]/page.tsx` : inchangé côté URL, passe l'UUID en prop à `ChallengeManageView`.
- `app/not-found.tsx` : 404 au style du site (il n'en existe qu'un pour `/contributors`).

**Point à vérifier en local :** `permanentRedirect` émet un vrai 308 hors contexte de streaming, mais une balise meta de redirection côté client s'il est levé après l'envoi du premier octet. Aucune page concernée n'a de `loading.tsx` ni de `Suspense` au-dessus : on attend un 308. Contrôle `curl -sI` avec un UA navigateur **et** un UA Googlebot. Si c'est une meta, repli : redirection des formes UUID dans `proxy.ts`, dont le matcher couvre déjà `/challenges/:path*`, à étendre à `/sandbox/:path*`.

### 5.3 Composants client — l'ID ne vient plus de `useParams()`

- `ChallengeDetailClient.tsx:132` : `challengeId` (UUID) et `challengeSlug` en props. Toutes les requêtes et clés de cache restent sur l'UUID ; les liens utilisent le slug.
- `ChallengeManageView.tsx:414` : `challengeId` en prop. Cache `['challenge-overview', uuid]` partagé avec la page publique, comme aujourd'hui. Redirections `:525,528` vers le slug lu dans l'overview.

## 8. Mode groupe

1. Lien d'invitation construit sur le slug : `/challenges/<slug>?group=<token>` (`ChallengeDetailClient.tsx:710`, `JoinModal.tsx:102`). Le jeton (`group_id`) et les routes `/api/challenges/<uuid>/group/*` et `/join` ne changent pas.
2. Liens déjà partagés `/challenges/<uuid>?group=<token>` → 308 vers `/challenges/<slug>?group=<token>`, **query conservée** ; même chose pour un ancien slug.
3. Notifications : `challengeSlug` dans les nouveaux payloads, repli sur l'UUID (→ redirection) pour les anciens. Acceptation : `POST /join` sur l'UUID, inchangé.
4. **Bug préexistant, corrigé dans ce chantier :** un visiteur **non connecté** qui ouvre un lien d'invitation perd le jeton à la connexion. Les liens `/signin?from=` ne portent pas `?group=`, et `safeInternalPath` refuse toute query (verrouillé par `lib/url.test.ts:44-46`). Il revient sur le challenge sans l'invitation et doit rouvrir le lien. Correctif, en commit séparé : `safeInternalPath` admet **exactement** un suffixe `?group=<uuid>` (rien d'autre), les deux liens de connexion le transmettent, tests mis à jour.
